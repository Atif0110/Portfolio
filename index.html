TrustLayer

agent infrastructure

An authorization layer for AI agents. Before an agent acts, it asks TrustLayer whether it is permitted, and anything consequential can be routed to a human first.

FastAPIPostgreSQLSQLAlchemy asyncAlembicReactDocker Composepytesttestcontainers
  • It fails closed. The evaluator walks policy rules in order, returns the first match, and when nothing matches it returns DENY with the reason recorded. Malformed rules are skipped rather than trusted, so a broken policy cannot widen access.
  • Policies are data, not code. Conditions match on action plus context, with numeric comparison operators for thresholds, so a rule like refunds under one hundred allowed and above that requiring approval is a row in the database that an operator can change without a deploy.
  • Policy changes are versioned per organization. Each update takes the next monotonic version number for that tenant, which means an audit entry can always be read against the exact policy that produced it rather than whatever is current today.
  • Human approval is a first class state. Actions resolving to require approval enter a queue and stay blocked until an owner signs off. Every decision lands in an append only log, and records are tenant scoped, so a second organization asking for another tenant's approval request receives a not found rather than a leak.
  • Built to be handed to a team. Continuous integration on every push runs linting, unit tests, and integration tests against a real PostgreSQL instance spun up through testcontainers, plus type checking and tests for the React dashboard. Schema changes go through Alembic migrations, and the whole stack comes up with Docker Compose and a seed script.

Power Price Forecasting Pipeline

applied machine learning

Day ahead electricity price forecasting for the German market, taken past the error metric into a data quality gate, calibrated uncertainty, and a signal layer that declines to act when it is not confident.

PythonXGBoostscikit learnpandasENTSOE APIPlotlyGroqpytest
  • Every run has to beat a named baseline. The model is scored against a seasonal naive benchmark, the price twenty four hours earlier, and the pipeline reports mean absolute error for both plus the percentage improvement. Complexity has to earn its place instead of being assumed.
  • The split respects time. Training and test sets are cut chronologically rather than shuffled, so no future information leaks backward into training, which is the failure mode that quietly inflates most time series results.
  • Features model the actual market. Hour, weekday, month and weekend flags for seasonality, lags at one, twenty four, forty eight and one hundred sixty eight hours, a rolling daily mean and standard deviation, and a momentum term, all on top of load and renewable generation as demand and supply drivers. Feature engineering raises immediately if any missing value survives it.
  • A quality gate that understands the domain. Before modeling, data is scored out of one hundred with deductions for missing hours, duplicate timestamps, extreme spikes, and violated economic relationships, since price should move with load and against wind and solar. The result is a structured report, so bad data is caught rather than silently trained on.
  • Uncertainty drives the decision. A ninety five percent interval is derived from training residuals and carried forward, and the signal layer takes a position only when the spread against the reference price exceeds that interval, otherwise it returns no trade. An LLM layer turns the run into a written trader brief, and the output is an interactive chart of forecast against actual with the signal and a cumulative simulation.

Simulated performance comes from a historical backtest of the signal rules against a fixed reference price and is not a claim about live trading.

AI Competitor Research Platform

LLM data pipeline

Agent driven competitive intelligence that answers what a competitor charges, in which market, and how that has moved, with every number traceable to the run that produced it.

PythonFastAPIFirecrawlPlaywrightSQLiteprovider fallbackRAGStreamlit
  • Geography is enforced, never inferred. Each URL is fetched once per execution region and the pipeline decides that region, not the model. If extraction claims a different one the mismatch is logged and the pipeline wins, and with strict verification enabled a scrape that cannot prove its exit location is refused rather than quietly returning the wrong market's prices.
  • Extraction corrects itself. Output is validated against a schema and a confidence check, and failures retry with the previous error fed back to the model. The provider chain is built across every fallback hop, and telemetry separates calls, attempts and fallbacks, with counters reset at the start of each run so metrics from one job never bleed into another.
  • Storage is idempotent with real provenance. An observation key hashes the canonical URL, product identity, region, competitor, seller and snapshot hour, while the run identifier stays as metadata rather than part of the key, so re running a job updates rather than duplicates and any single run remains recoverable. Raw page content and a hash are kept per URL for debugging bad extractions.
  • Reports cannot silently mix runs. Every analysis method filters by run in SQL rather than in Python, so a report for one run can never blend observations from another, and reads come from a single per run metrics table that the dashboard, the PDF and the alerts all share.
  • It refuses to guess when the input is wrong. Product filtering matches the URL path only, with word boundaries so a short token cannot match unrelated segments, and when nothing matches it returns zero URLs with a warning instead of broadening to scrape the entire site. Checkpoints survive corruption by restarting cleanly rather than crashing.

Shravan

full stack product

A health companion for senior citizens and their caretakers covering medicine reminders, health logging, emergency contacts, nearby care discovery and AI assistance, across a web app and a mobile client.

FlaskSQLAlchemyVue 3PiniaFlutterGroqGeminiSwagger
  • One backend, two clients. A single Flask and SQLAlchemy API serves both the Vue web application and the Flutter mobile client, running on SQLite by default and moving to PostgreSQL through one connection string with no code change.
  • Security treated as a requirement. Server side sessions, password hashing, cross site request forgery protection on state changing requests, login throttling, session expiry, role checks, restrictive origin policy, response security headers, request size limits, user scoped data access, and validation of user supplied external URLs. API keys stay on the backend and never reach the client.
  • It degrades instead of failing. Healthcare discovery uses Google Places when a key is configured and falls back to OpenStreetMap, with geocoding falling back to Nominatim, so the core flow works at zero API cost and the product is never one billing problem away from being unusable.
  • Documented and testable. Interactive API documentation is generated per endpoint and served from the running backend, with a pytest suite and single command startup scripts for both Windows and Unix.
  • Explicit safety boundary. The assistant is scoped in product to general information and is stated not to be a diagnosis or a substitute for a clinician, with emergency symptoms routed to real services. Placed fifth of thirty at an IIT Madras competition.

OpenClaw

automation agent

Describe a task in plain English and it becomes a scheduled browser agent, previewed and approved by you before it is allowed to run, entirely on your own machine.

Node.jsExpressPlaywrightnode cronSQLiteOllamaOpenAI
  • Local first by default. A router selects a local model through Ollama when no API key is present and a hosted model when one is, so the entire system can run offline with nothing leaving the machine.
  • Nothing executes without consent. Each generated agent is rendered as a preview showing its goal and schedule and requires explicit approval before deployment, with a sandboxed dry run available first.
  • Scheduled execution against a real browser. Approved agents are handed to a cron scheduler that drives a Chromium instance through Playwright, with agent configuration, credentials and execution logs persisted locally in SQLite.
  • Small and legible. The server, router, agent manager, scheduler, browser layer and database each live in one focused module, which makes the approval boundary easy to audit rather than buried in a framework.
